# Prompt: Build the CSE731 Software Testing Agentic AI Mini Project

You are an expert Python software engineer and software-testing researcher. Build a complete, runnable mini project for the IIIT Bangalore CSE731 Software Testing mid-term project described in the supplied project brief. The objective is to implement, from first principles, an agentic AI pipeline that takes programming problems from a benchmark dataset, generates unit-level implementation code, generates unit tests specifically targeted at a user-specified testing requirement, executes those tests, measures the actual testing result, and returns an objective verdict. For this implementation, choose **coverage-based unit testing**, specifically **decision/branch coverage**, because the project requirement explicitly permits coverage criteria such as statement, loop, and decision coverage and requires the test-case generator to generate tests satisfying the selected criterion. The pipeline must contain at least these three clearly separated agents: **(1) Code Generator Agent**, which receives a dataset problem and generates executable Python implementation code; **(2) Test Case Generator Agent**, which receives the generated code plus the explicit testing goal and generates executable unit tests intended to achieve decision/branch coverage; and **(3) Test Case Executor Agent**, which executes the generated implementation and tests in an isolated/safely controlled subprocess environment, collects pass/fail information and actual coverage information, compares the achieved coverage against the required testing goal, and produces a structured verdict. Do not implement the project as a single LLM call with three labels; each agent must have a distinct responsibility, input/output contract, prompt/configuration, and execution stage, and the pipeline must explicitly pass the output of one agent to the next. Do **not** use RAG, vector databases, embeddings/retrieval, LangGraph, CrewAI, AutoGen, chain-of-thought frameworks, or any other agent orchestration framework prohibited by the course brief; implement the orchestration yourself using ordinary Python modules/classes/functions and explicit control flow so that the project demonstrates first-principles agentic pipeline construction. Use an LLM through a configurable API provider such as OpenRouter or another OpenAI-compatible endpoint, with the API key supplied through environment variables; never hard-code credentials. Use structured JSON outputs from the LLM agents wherever possible and validate those outputs before allowing them into the next stage. Use a strong Python-capable coding model available through the configured provider, but keep the model/provider configurable through environment variables or a configuration file. Record model name, temperature, max tokens and other relevant generation parameters in the experiment configuration and result files because the project brief requires these settings to be documented later. For the dataset, use **HumanEval and MBPP as candidate benchmark sources**, but do not simply process arbitrary trivial examples: implement a curated selection/filtering mechanism that favors problems whose reference/solution code contains meaningful control flow, such as multiple conditional branches, nested conditions, loops with meaningful edge cases, early returns, boundary conditions, or multiple logical paths. Prefer approximately **15–25 high-quality problems** for the initial experiment so the project remains manageable, and ensure that the selected problems are suitable for meaningful decision/branch coverage. The program should be able to load either HumanEval or MBPP through a clean dataset adapter, normalize their different schemas into one internal representation, and support a deterministic curated subset via a checked-in selection/configuration file so experiments are reproducible. Do not claim that the entire benchmark is processed if only a subset is used. Before generating tests, the Test Case Generator Agent must receive an explicit testing objective such as `decision_coverage` and instructions to reason about the control-flow decisions present in the generated code; it should generate tests for true and false outcomes of relevant decisions and include important boundary/edge cases, while avoiding redundant tests where possible. The generated test suite must be actual executable Python tests, preferably using pytest, and must not merely be natural-language test descriptions. The Test Generator Agent must return both the tests and concise machine-readable metadata explaining the intended coverage targets, such as branch/decision conditions or test categories, but do not require or expose hidden chain-of-thought. The system must treat the LLM's claimed coverage as untrusted: actual coverage must be measured by executing the generated tests against the generated implementation using an appropriate Python coverage mechanism. If branch/decision coverage cannot be measured reliably for a particular generated program, mark the case as unsupported or failed rather than fabricating a coverage value. The implementation should use a suitable Python coverage library/tool capable of branch measurement, and the final verdict must be based on measured execution results rather than the LLM's statement. Define a clear success criterion, for example: tests execute successfully and the measured branch/decision coverage reaches the configured target, such as 100% of measurable branches; if the target is not achieved, the result must be `FAIL` or `TARGET_NOT_MET` with the missing coverage information. Include a bounded feedback loop so that, when the first generated test suite does not achieve the required coverage, the Test Case Generator Agent can receive the executor's structured coverage feedback and generate an additional/refined test suite, subject to a configurable maximum number of iterations such as 2 or 3. The loop must terminate when the target is achieved, the maximum iterations are exhausted, or execution fails unrecoverably. This feedback loop should be explicit in the pipeline and should demonstrate why the system is agentic rather than simply performing three independent API calls. Keep the implementation deterministic where practical by fixing random seeds for dataset selection and recording all relevant settings, while still allowing the LLM temperature to be configured. The generated Python code and tests must be stored per problem in an organized output directory, together with raw/parsed agent outputs where appropriate, execution logs, coverage reports, and a final structured result such as JSON. Add robust validation and failure handling for malformed LLM responses, syntax errors in generated code, invalid tests, timeouts, runtime exceptions, coverage-tool failures, API failures, and cases where the generated implementation does not conform to the expected function signature. Never execute arbitrary generated code directly inside the main Python process; use a subprocess with timeout/resource safeguards and a clearly documented execution directory. Do not attempt to bypass operating-system security protections; this is an academic local project and should use a reasonable controlled execution approach. The executor should capture stdout, stderr, exit status, test counts, passed/failed tests, traceback/error information, branch coverage percentage, total measurable branches, covered branches, missing branches where available, and the final verdict. Create a unified internal data model for a problem, generated code, generated tests, execution result, coverage result, and final verdict. Include a simple command-line interface so the user can run the entire pipeline, run one problem, run a selected dataset, or run the experiment over the curated subset. Provide commands such as `setup`, `list-problems`, `run-one`, and `run-experiment` if practical, but keep the interface simple. Include a dry-run/mock mode that does not call an LLM and can be used to verify the pipeline structure and executor/coverage infrastructure, but make it obvious in the output that mock mode is not an actual AI experiment. The real mode must use the configured LLM API. Include unit tests for the project's own non-generated components, especially dataset normalization, response parsing/validation, coverage-result parsing, verdict calculation, retry/iteration logic, and configuration loading. Do not confuse these project unit tests with the generated benchmark tests; clearly separate them. Produce a clean repository with a `README.md` that explains prerequisites, Python version, virtual-environment setup, dependency installation, API-key/provider configuration, dataset preparation/download, configuration, how to run a smoke test, how to run one problem, how to run the full curated experiment, where generated code/tests/results/coverage reports are stored, troubleshooting, safety considerations for generated-code execution, and the exact architecture of the three agents. Include a `.env.example` but never include a real API key. Include `requirements.txt` or an equivalent reproducible dependency file. Include configuration files for model/provider settings and the curated problem selection. Include an experiment-results schema and example result. The README should explain that the project deliberately does not use RAG, LangGraph, CrewAI, AutoGen, vector databases, or chain-of-thought frameworks because the course brief explicitly prohibits such approaches. Do not build report-generation functionality or presentation/demo functionality now; focus only on the working project implementation and startup/run documentation. Do not fabricate benchmark records or pretend to have executed an external API call if the environment is not configured. If network access or dataset download is unavailable, provide a clear setup command/instruction and a local-file fallback, but still make the code ready to run once the dataset is available. Prefer a modular architecture such as `agents/`, `datasets/`, `execution/`, `evaluation/`, `models/`, `config/`, `prompts/`, `experiments/`, `tests/`, and `outputs/`, but choose the final structure based on maintainability. Keep prompts as versioned text/templates in the repository rather than embedding huge prompts directly in Python source. The Code Generator Agent prompt should require only the requested function implementation and a machine-readable response, without explanations or hidden reasoning. The Test Generator Agent prompt should require executable tests, explicit coverage intent metadata, and no chain-of-thought. The Executor Agent should primarily be a deterministic software component that invokes the test/coverage tools and converts their measured outputs into a verdict; if an LLM is used for interpretation, it must never override the measured coverage or execution result. Ensure the final implementation clearly demonstrates this data flow: `Dataset Problem -> Code Generator Agent -> Generated Code -> Test Generator Agent -> Generated Tests -> Test Case Executor Agent -> Actual Test/Coverage Results -> Coverage Evaluation -> PASS/FAIL/TARGET_NOT_MET`, with the optional bounded feedback loop returning coverage feedback to the Test Generator Agent. Include representative examples using non-trivial benchmark problems rather than toy examples such as simple addition, even/odd, or basic maximum-of-two-number exercises. The final code must be complete and runnable, not pseudocode, and all imports, configuration files, prompts, schemas, CLI commands, and README instructions must be internally consistent. Before presenting the final implementation, perform a consistency check across file paths, module imports, configuration names, environment variables, CLI commands, output schemas, and README commands. Clearly identify any assumptions that cannot be verified locally. The final response should first give a concise architecture summary, then provide the complete project files/code, followed by the exact startup and execution instructions in the README; do not include the course report or demo material.
